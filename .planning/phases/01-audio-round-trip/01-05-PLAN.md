## Phase Goal

**As a** musician (or the AI agent I tell to run tests), **I want to** measure my audio round trip from the `soundping` CLI, **so that** I get a trustworthy, saved number on the engine every later recipe reuses.

<objective>
Let users and agents see what is on the machine and pick it unambiguously: list audio and MIDI devices by stable ID, resolve selectors and named setups through one resolver, and never fall back to a system default (ENG-01, D-07..D-11). Also ship the small discovery verbs `recipes` and `paths` (D-02, D-06).

Purpose: nothing may be hard-wired to Flo's gear, and a number measured on the wrong device is worse than no number. D-07: this selection model is provisional, so the setups schema stays small and versioned.
Output: HAL + CoreMIDI catalog, simulated catalog, SetupResolver, setups.json, `devices`/`recipes`/`paths` commands, device flags on `run`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HAL / CoreMIDI → engine | device names and properties come from drivers (including third-party and virtual devices) |
| setups.json on disk → resolver | user- or agent-edited config file |
| CLI selectors → resolver | free-text selectors from an agent |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-16 | Spoofing | device selection by name | high | mitigate | exact-UID precedence, exact-name over substring, ambiguity is an error listing UIDs, `default` pinned to a UID and printed (D-08, D-10) |
| T-01-17 | Denial of service | setups.json decode | medium | mitigate | typed Codable decode with schemaVersion check → usage error setupsUnreadable naming the file, never a crash (ASVS V5) |

| T-01-SC | Tampering | SwiftPM installs | high | mitigate | no new packages |
</threat_model>
